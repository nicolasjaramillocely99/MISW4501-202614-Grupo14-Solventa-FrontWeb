# `src/app/core` — servicios transversales (singletons)

Todo lo que existe una sola vez en la aplicación y no tiene interfaz visual. Se registra en `app.config.ts` y lo consumen `features` y `layout`. `core` no importa de `features`.

| Carpeta | Responsabilidad | Vínculo con la arquitectura |
|---|---|---|
| `auth/` | Sesión del usuario, proveedor de identidad (Amazon Cognito User Pool, OIDC), modelo de roles. **HA-S01:** `sesion.service.ts` (`SesionService`: señales `sesion`, `usuario`, `rol`, `autenticado` y `expirada`; tokens en memoria y token de renovación en `sessionStorage`; renovación un minuto antes del vencimiento; `RevokeToken` al cerrar sesión), `proveedor-identidad.ts` (puerto `ProveedorIdentidad` y `ErrorIdentidad`), `cognito-proveedor-identidad.service.ts` (API JSON de Cognito: `InitiateAuth` con `USER_PASSWORD_AUTH` y `REFRESH_TOKEN_AUTH`, y `RevokeToken`; endpoint regional de AWS salvo que el ambiente defina `cognito.endpoint`, como el local con el emulador Moto; se enlaza al puerto en `app.config.ts`), `decodificar-jwt.ts` (lee claims sin verificar la firma) y `modelos/{rol,sesion}.ts` (grupos `insured`, `advisor`, `operations` y `partner` → roles) | HA-S01 · EC-S03. Los cuatro roles humanos: asegurado, asesor comercial, analista de operaciones, socio comercial |
| `auth/guards/` | `autenticacion.guard.ts` (recupera la sesión con el token de renovación; sin sesión → `/acceso/iniciar-sesion?returnUrl=…`; sesión vencida sin renovación → `/acceso/sesion-expirada`) y `rol.guard.ts` (`rolGuard(...roles)`; rol insuficiente → `/acceso/no-autorizado`) | 401 / 403 definidos en HA-S01 |
| `auth/interceptores/` | `autenticacion.interceptor.ts`: adjunta el ID token (`Authorization: Bearer`) **solo** a las peticiones a `<apiGatewayUrl>/v1/…` (T5: en la nube `apiGatewayUrl` es el propio portal, así que `config.json`, los diccionarios y `/pasarela/*` nunca llevan el token, y un 403 de la pasarela no lleva a «no autorizado»); ante 401 renueva el token (`SesionService.renovarAhora`, `REFRESH_TOKEN_AUTH`) y reintenta la petición **una vez**; si no se puede renovar o el reintento vuelve a dar 401, expira la sesión y lleva a `/acceso/sesion-expirada`; ante 403 lleva a `/acceso/no-autorizado`, sin reintentar | El *authorizer* de Cognito valida el token en el gateway |
| `configuracion/` | **T5:** configuración del ambiente leída **antes de arrancar** (decisión D-5): `configuracion.ts` (`ConfiguracionEjecucion` con `apiGatewayUrl`, `pasarelaPagosUrl` y `cognito`; *token* `CONFIGURACION_EJECUCION`; `ErrorConfiguracion`) y `cargar-configuracion.ts` (`cargarConfiguracion`: en local usa `environment.configuracionLocal`; en la nube pide `config.json` al origen del portal, sin caché, y valida URL `https://` —o `http://localhost`—, identificadores no vacíos y región de AWS; `mostrarAvisoConfiguracion` muestra el aviso fijo y bilingüe de `index.html`). `main.ts` la carga y la provee; sin configuración válida el portal no arranca ni llama a nada. `config.json` lo escribe Terraform junto al sitio (backend, `infra/terraform/modules/web-portal`); un mismo *build* sirve a staging y a production-demo | Portal servido por CloudFront con el API en el mismo dominio |
| `api/` | Cliente HTTP base (URL del API Gateway desde `CONFIGURACION_EJECUCION`) y **un cliente por microservicio** | Conector «solicitudes del portal» → API Gateway «Facade» |
| `api/originacion/` | Cotización, emisión, cobro, endosos, renovación, cancelación. **HU-W1.2-02:** `originacion-api.service.ts` (`OriginacionApiService.resolverPerfilRiesgo`, `POST /v1/risk-profiles/resolve`) y `perfil-riesgo.modelos.ts` (tipos según el `openapi.yaml` del backend v0.3.0 y traducción snake_case → camelCase). **HU-W1.3-01:** `aceptarOferta` (`POST /v1/offers/{offer_id}/acceptance`), `consultarAceptacion` (`GET /v1/acceptances/{acceptance_id}`) y `consultarAceptacionDeOferta` (`GET /v1/offers/{offer_id}/acceptance`); `aceptacion.modelos.ts` (tipos según el `openapi.yaml` v0.4.0 y `ErrorAceptacion` con el código estable `error` del contrato; sin cuerpo JSON, un error de red o 5xx se trata como el 503 del endpoint) | Servicio de originación **HU-W1.1-01:** `cotizacion-asistida.modelos.ts` y los métodos `buscarClientePorDocumento`, `crearCotizacionAsistida` y `consultarCotizacionAsistida` de `OriginacionApiService` (`GET /v1/customers`, `POST` y `GET /v1/assisted-quotes`). **HU-W1.3-03:** `emision-contractual.modelos.ts` y `consultarEmisionContractual` / `descargarDocumentoContractual` (`GET /v1/policies/{id}/issuance-status` y `/contract-document`). **HA-D02:** `consultarCobro` (`GET /v1/acceptances/{acceptance_id}/charge`) y `cobro.modelos.ts` (tipos según el `openapi.yaml` v0.7.0, `esCobroFinal` y `ErrorCobro` con el código estable `error`; sin cuerpo JSON se trata como `charge_unavailable`). **HU-W1.1-02:** `listarSolicitudesRevision` (`GET /v1/review-requests?status=&order=&reason=`), `consultarSolicitudRevision` (`GET /v1/review-requests/{acceptance_id}`) y `registrarDecision` (`POST /v1/review-requests/{acceptance_id}/decision`); `revision.modelos.ts` (tipos según el `openapi.yaml` v0.8.0 y `ErrorRevision`; sin cuerpo JSON, un 5xx se trata como `review_unavailable` en las lecturas y `decision_not_registered` en el registro); `aceptacion.modelos.ts` suma los estados `adjusted` y `rejected` y la `revision` del asesor con la oferta ajustada. **HU-W1.2-03:** `generarOferta` (`POST /v1/offers`), `consultarOferta` (`GET /v1/offers/{offer_id}`) y `renovarOferta` (`POST /v1/offers/{offer_id}/renewal`); `oferta.modelos.ts` (tipos según el `openapi.yaml` v0.10.0 y `ErrorOferta` con el código estable `error` del contrato —`superseded_by` en `offer_superseded`, `expires_at` en `offer_still_valid`—; sin cuerpo JSON, un error de red o 5xx se trata como `offer_unavailable`; las ofertas `adjusted` y `demo` llegan con una vista reducida). |
| `aliado/` | **HU-W1.2-02:** `contexto-aliado.service.ts` (`ContextoAliadoService`): nombre del banco aliado que publica la pantalla del flujo y lee el shell embebido, para no importar `features` desde `layout` | Canal embebido |
| `api/siniestros/` | Radicación, consulta, triage, evaluación, asistencias | Servicio de siniestros |
| `api/socios/` | Alta de socios, credenciales, tablero de desempeño | Servicio de gestión de socios B2B |
| `api/auditoria/` | Consulta de trazabilidad y consentimientos. **HU-W1.2-01:** `auditoria-api.service.ts` (`AuditoriaApiService.consultarTerminosVigentes`, `GET /v1/audit/consent-terms/current`, y `registrarConsentimiento`, `POST /v1/audit/consents` con canal `embedded`) y `consentimiento.modelos.ts` (tipos según el `openapi.yaml` v0.2.0, traducción snake_case → camelCase y `ErrorConsentimiento` con el código estable `error` y los campos de `validation_failed`; sin cuerpo JSON se trata como `service_unavailable`). La verificación y la evidencia no se consumen desde el canal embebido | Servicio de auditoría y consentimientos |
| `i18n/` | Configuración de Transloco (carga de `public/i18n/*.json`), idioma activo y formateo de moneda, fecha y número con la API `Intl`. **HA-S01:** `transloco.config.ts` (`proveerI18n`: `es-CO` predeterminado, `en-US` alterno y respaldo en `es-CO`; al arrancar restaura el idioma elegido), `cargador-traducciones.ts` e `idioma.service.ts` (`IdiomaService`: idioma activo, cambio en caliente, atributo `lang` del documento y preferencia en `localStorage`, que se conserva al pasar de P0 al portal) | OBJ 12 · soporte multimoneda (COP, MXN, CLP, PEN) |
| `navegacion/` | Menú de la barra lateral por rol y ruta de inicio de cada rol. **HA-S01:** `menu-por-rol.ts` (`MENU_POR_ROL`, `RUTA_INICIO_POR_ROL` e `itemActivo`) | Barra lateral «los ítems cambian según el rol» |
| `errores/` | `ErrorHandler` global, identificador de correlación en las peticiones y manejo uniforme de errores HTTP | Observabilidad con trazas correlacionadas |

Interceptores sugeridos (en este orden): correlación → autenticación → errores HTTP.

El servicio de notificaciones **no** tiene cliente aquí: el cliente web no lo consume (sus eventos llegan por *push* a la app móvil).
